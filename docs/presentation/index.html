Stage 4 of 8 · Safety net

Record, replay, compare

1

Choose inputs

The business cases, ideally replayed from production.

2

Record

Run them on the legacy. Every output becomes an approved snapshot.

3

Replay

Run the same inputs on the new system and compare.

4

Review

Every difference is a defect, or a change agreed on purpose.

Test at the edges: API responses, screens, files, messages, the database after an operation. They still mean something after the migration.

The golden master: characterization tests at scale, after Michael Feathers

Stage 6 of 8 · Dual-run

Run both, always return the control

Shadow reads

The facade asks both, returns the legacy answer, and compares in the background. Cheap and safe: run it for every slice.

Used here

Shadow writes

The new system computes each write on its own copy, every side effect off. Harder, and catches the most important bugs.

Parallel batches

Both versions of a batch run on the same input. Outputs are compared record by record.

Every mismatch is stored with the input that produced it, so a developer can replay it.

Control and candidate: the shape popularised by GitHub’s Scientist

Stage 8 of 8 · Decommission

The step that delivers the savings

Decided in advance

· a stable period

· no rollback needed

· every consumer moved

1

Stop the reverse sync

2

Archive what retention requires

3

Remove the code, adapters, flags and routes

4

Drop the tables, switch off the servers, end the licences

The strangler that never finishes: migrations stall at 80% and two systems run forever. Give each slice a decommission date.

Lessons

Five things to take away

1

Small steps, not a big bang

Move one slice at a time, and finish each one.

2

The old code is the real spec

Find the rules nobody wrote down first.

3

Data first

Plan the data move before the new screens.

4

Prove it before you switch

Tests and comparisons decide, not opinions.

5

Keep a way back

Until the last step, undo is one command.
